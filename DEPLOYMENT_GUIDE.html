Secure Photo Gallery

End-to-end deployment guide for the AWS serverless photo app — CloudFront, S3, Lambda, API Gateway, Cognito & DynamoDB.

Region: ap-south-1 CloudFront + OAC Private S3 + Presigned URLs Cognito Auth

Overview & Architecture

This is a secure, multi-user photo gallery. The static frontend is delivered over HTTPS by Amazon CloudFront, which reads the files from a private S3 bucket via Origin Access Control (OAC) — the bucket itself is never public. Users authenticate through a Cognito hosted UI, upload images to a separate private data bucket, and view only their own photos. The browser never holds S3 credentials; Lambda issues short-lived presigned URLs for every upload and view.

   Browser  ──HTTPS──▶    │  Amazon CloudFront (CDN)     │
   (app UI)              │  · Default root: index.html  │
       ▲                 │  · OAC (SigV4 signed)        │
       │                 └───────────────┬──────────────┘
       │                                 │ reads site files (private)
       │                                 ▼
       │                 ┌──────────────────────────────┐
       │                 │  S3: hosting bucket (PRIVATE)│  ← bucket policy allows
       │                 │  index.html, logo.png        │    only this distribution
       │                 └──────────────────────────────┘
       │
       │  1. Sign in (OAuth implicit) ───────────────▶ Cognito Hosted UI ──▶ id_token (JWT)
       │
       │  2. POST /photos  (Authorization: id_token)
       ▼
   API Gateway (REST) ──[Cognito Authorizer validates JWT]──▶ Lambda: uploadPhoto
       │                                                          │ writes metadata + userSub
       │                                                          ▼
       │                                                      DynamoDB (PhotoGallery)
       │  ◀── presigned PUT URL (5 min) ──────────────────────────┘
       │  3. PUT file directly to S3 (private DATA bucket)
       │
       │  4. GET /photos  (Authorization: id_token)
       ▼
   API Gateway ──[Authorizer]──▶ Lambda: listPhotos ──▶ DynamoDB (filter by userSub)
       │  ◀── list + presigned GET URLs (15 min) ──┘
       ▼
   Browser renders the signed-in user's photos (img src = presigned S3 URL)
Two private buckets, two jobs. The hosting bucket serves the website but only through CloudFront (OAC). The data bucket stores photos and is reached only via Lambda-issued presigned URLs. Neither bucket is public.
What changed vs. S3 website hosting? The site is no longer served from the public S3 website endpoint. CloudFront sits in front of a private bucket, giving you HTTPS, a CDN edge cache, and no public bucket. The app URL becomes https://<dist-id>.cloudfront.net/. The frontend code is unchanged — it derives its OAuth redirect URI from the current page URL at runtime.

Prerequisites

  • An AWS account with permissions for S3, CloudFront, Lambda, API Gateway, Cognito, DynamoDB and IAM.
  • AWS CLI v2 configured (aws configure) — optional, used for the CLI shortcuts.
  • A modern browser. For local testing, the Live Server VS Code extension (serves on localhost:5500).
  • Project files: lambda/uploadPhoto.py, lambda/listPhotos.py, s3/index.html, s3/logo.png.
Region rule. Put S3, Lambda, API Gateway, Cognito and DynamoDB all in ap-south-1. CloudFront is global (no region) and its default certificate already covers *.cloudfront.net, so HTTPS works out of the box.

1Create the DynamoDB Table

One metadata item per uploaded photo (including the owner's Cognito userSub).

Console

  1. DynamoDB → Create table.
  2. Table name: PhotoGallery
  3. Partition key: photoId — type String. (No sort key.)
  4. Capacity: On-demand.
  5. Create table.

CLI

aws dynamodb create-table \
  --table-name PhotoGallery \
  --attribute-definitions AttributeName=photoId,AttributeType=S \
  --key-schema AttributeName=photoId,KeyType=HASH \
  --billing-mode PAY_PER_REQUEST \
  --region ap-south-1
DynamoDB is schemaless — the other fields (filename, s3Key, userSub, userEmail…) are written by Lambda at upload time.

2Create the S3 Buckets (both private)

Two buckets, both with Block all public access ENABLED. Bucket names are globally unique — adjust if taken.

2a · Private data bucket — aviz-photo-secure-data-hosting

  1. S3 → Create bucket in ap-south-1.
  2. Keep “Block all public access” ENABLED.
  3. Create the bucket.
  4. Open it → Permissions → CORS → paste the JSON from the CORS reference (required for presigned PUT uploads / GET views from the browser).
# CLI equivalent
aws s3api create-bucket --bucket aviz-photo-secure-data-hosting \
  --region ap-south-1 --create-bucket-configuration LocationConstraint=ap-south-1

aws s3api put-bucket-cors --bucket aviz-photo-secure-data-hosting \
  --cors-configuration file://s3/cors.txt --region ap-south-1

2b · Private hosting bucket — aviz-photo-static-web-hosting

  1. S3 → Create bucket in ap-south-1.
  2. Keep “Block all public access” ENABLED. (CloudFront, not the public internet, will read it.)
  3. Do NOT enable static website hosting, and do not add a public bucket policy. The OAC policy is added in Step 3.
  4. Create the bucket.
aws s3api create-bucket --bucket aviz-photo-static-web-hosting \
  --region ap-south-1 --create-bucket-configuration LocationConstraint=ap-south-1
Don't upload the frontend yet. index.html needs the API URL, Cognito domain and Client ID first — you'll set those and upload in Step 9, then invalidate the CloudFront cache.

3Create the CloudFront Distribution (with OAC)

CloudFront serves the site over HTTPS and is the only thing allowed to read the private hosting bucket.

Console

  1. CloudFront → Create distribution.
  2. Origin domain: choose your hosting bucket from the list. Pick the bucket's REST endpoint (e.g. aviz-photo-static-web-hosting.s3.ap-south-1.amazonaws.com), not a “website endpoint”.
  3. Origin access: select Origin access control settings (recommended) → Create new OAC → keep defaults (Sign requests, SigV4) → Create.
  4. Viewer protocol policy: Redirect HTTP to HTTPS.
  5. Default root object: index.html. (Critical — without it, opening / returns AccessDenied.)
  6. Leave WAF off for now. Create the distribution.
  7. CloudFront shows a banner: “The S3 bucket policy needs to be updated.” Click Copy policy, then go to the hosting bucket → Permissions → Bucket policy → Edit → paste → Save. (This is the OAC policy shown in the reference.)
  8. Wait until Status = Deployed (~5–15 min). Note the Distribution domain name, e.g. d1234abcd.cloudfront.net — this is your app URL.
REST endpoint, not website endpoint. OAC only works with the S3 REST/API endpoint (it signs requests with SigV4). If you point the origin at an S3 website endpoint, OAC signing won't apply and you'll get 403s. The console's bucket picker gives you the REST endpoint by default.
Default root object only covers /. This app is a single page at the root, so index.html is enough. (If you later add client-side routes, add a custom error response mapping 403/404 → /index.html.)

4Create the IAM Role for Lambda

Both Lambda functions share one execution role.

  1. IAM → Roles → Create role → Trusted entity: AWS service → Lambda.
  2. Attach:
    • AWSLambdaBasicExecutionRole — CloudWatch Logs.
    • AmazonDynamoDBFullAccess — read/write the metadata table.
    • AmazonS3FullAccess — generate presigned URLs & read/write objects.
  3. Name it PhotoGalleryLambdaRole and create.
Least-privilege upgrade (production). Scope the *FullAccess policies down to the specific table ARN and the data bucket ARN, allowing only dynamodb:PutItem/Scan/Query and s3:PutObject/GetObject.

5Create the Lambda Functions

Two functions, both Python 3.12, both using the Step 4 role.

5a · uploadPhoto

  1. Lambda → Create function → Author from scratch.
  2. Name: uploadPhoto · Runtime: Python 3.12 · Role: PhotoGalleryLambdaRole.
  3. Paste the code from lambda/uploadPhoto.py and Deploy.
  4. Configuration → Environment variables:

    PHOTO_BUCKET_NAME = aviz-photo-secure-data-hosting

  5. Configuration → General → Timeout: 30 seconds.

5b · listPhotos

  1. Create function listPhotos, same runtime and role.
  2. Paste the code from lambda/listPhotos.py and Deploy.
  3. Add env var PHOTO_BUCKET_NAME = aviz-photo-secure-data-hosting.
  4. Timeout: 30 seconds.
The table name PhotoGallery is hard-coded as TABLE_NAME in both files. If your table differs, edit that constant.
Per-user isolation is built in. listPhotos reads the caller's Cognito userSub from the authorizer claims and returns only that user's photos — see Per-User Isolation.

6Create the API Gateway

6a · REST API and resource

  1. API Gateway → Create API → REST API → Build.
  2. Name: PhotoGalleryAPI · Endpoint type: Regional.
  3. Create Resource → name photos (path /photos) → tick Enable API Gateway CORS.

6b · Methods

  1. /photos → Create Method → GET: Lambda Function, Lambda Proxy integration ON, function listPhotos.
  2. /photos → Create Method → POST: Lambda proxy ON, function uploadPhoto.
Lambda Proxy integration must be ON. The code reads event['requestContext']['authorizer']['claims'] and event['body'], which only exist with proxy integration.

6c · CORS on the resource

Select /photos → Enable CORS. Allow these headers:

Content-Type,Authorization,X-Amz-Date,X-Api-Key,X-Amz-Security-Token

Allow methods GET, POST, OPTIONS. For origin, use your CloudFront URL in production (e.g. https://d1234abcd.cloudfront.net) or * for a demo.

6d · Deploy to a stage

  1. Deploy API → New stage → name prod.
  2. Copy the Invoke URL, e.g. https://xgq35x32mg.execute-api.ap-south-1.amazonaws.com/prod (needed in Step 9).
You'll deploy again after attaching the Cognito authorizer (Step 8).

7Set Up Cognito Authentication

7a · User Pool

  1. Cognito → Create user pool. Sign-in option: Email.
  2. Pool name: PhotoGalleryUsers.
  3. Optionally disable “Prevent user existence errors” for easier demo debugging (re-enable for production).

7b · App Client

  1. Create a public app client with no client secret (browser app).
  2. Enable auth flows: ALLOW_USER_SRP_AUTH, ALLOW_CUSTOM_AUTH, ALLOW_REFRESH_TOKEN_AUTH.
  3. Note the App client ID (e.g. 2uuqj6jihv0obq9glvsvei72ce) for Step 9.

7c · Hosted UI domain

App integration → Domain → create e.g. avizway → avizway.auth.ap-south-1.amazoncognito.com.

7d · Hosted UI / OAuth settings

  • Identity providers: Cognito user pool.
  • OAuth grant type: Implicit grant.
  • Scopes: email, openid.
  • Allowed callback URLs — use your CloudFront domain (add both forms, plus localhost for dev): 
    https://d1234abcd.cloudfront.net/
https://d1234abcd.cloudfront.net/index.html
http://localhost:5500/index.html
  • Allowed sign-out URLs: the same set.
Callback URL must match exactly. The frontend uses window.location.href (minus the hash) as the redirect URI. Opening https://d123.cloudfront.net/ sends …/; opening …/index.html sends …/index.html. Register both so either entry point works — otherwise you get a redirect_mismatch error.
Replace d1234abcd.cloudfront.net everywhere with your real distribution domain from Step 3.

8Attach the Cognito Authorizer to API Gateway

  1. API Gateway → PhotoGalleryAPI → Authorizers → Create New Authorizer.
  2. Type: Cognito · Name: CognitoAuth · User pool: PhotoGalleryUsers.
  3. Token source: Authorization (exactly this — not “Bearer Authorization”).
  4. For both GET and POST: Method Request → set Authorization to CognitoAuth.
  5. Deploy API → prod to apply.
The frontend sends the raw id_token (no Bearer prefix). Keep the token source as Authorization to match.

9Configure, Upload & Invalidate the Frontend

Edit the two config blocks near the top of the <script> in s3/index.html:

const COGNITO_CONFIG = {
    domain: 'avizway.auth.ap-south-1.amazoncognito.com',   // Step 7c
    clientId: '2uuqj6jihv0obq9glvsvei72ce',                // Step 7b
    redirectUri: window.location.href.split('#')[0],       // auto → CloudFront URL
    region: 'ap-south-1'
};

const CONFIG = {
    API_URL: 'https://xgq35x32mg.execute-api.ap-south-1.amazonaws.com/prod', // Step 6d
    S3_BUCKET_NAME: 'aviz-photo-secure-data-hosting',      // DATA bucket (Step 2a)
    AWS_REGION: 'ap-south-1',
    S3_REGION: 'ap-south-1'
};

Upload the site files to the hosting bucket, then invalidate the CloudFront cache so edges fetch the new version:

aws s3 cp s3/index.html s3://aviz-photo-static-web-hosting/index.html --region ap-south-1
aws s3 cp s3/logo.png  s3://aviz-photo-static-web-hosting/logo.png  --region ap-south-1

# Bust the CDN cache (replace with your distribution ID)
aws cloudfront create-invalidation --distribution-id E123ABCXYZ --paths "/*"

Your live URL is the CloudFront domain:

https://d1234abcd.cloudfront.net/

Always invalidate after re-uploading index.html. CloudFront caches at the edge; without an invalidation (or versioned filenames) users keep getting the old page. /* invalidations are free up to 1,000 paths/month.
Confirm this exact CloudFront URL is in the Cognito callback & sign-out lists (Step 7d), or sign-in fails.

10Create a Test User

Either self-register via the hosted UI's Sign up link, or create one manually:

  1. Cognito → PhotoGalleryUsers → Users → Create user.
  2. Enter an email, set a password, mark email verified / password permanent for testing.
aws cognito-idp admin-create-user --user-pool-id <POOL_ID> \
  --username you@example.com --region ap-south-1

aws cognito-idp admin-set-user-password --user-pool-id <POOL_ID> \
  --username you@example.com --password '<StrongPassw0rd!>' \
  --permanent --region ap-south-1
Never commit real passwords to source files or version control. Rotate any password that has been written to a shared file.

11Test the Full Flow

  1. Open https://<dist-id>.cloudfront.net/ → sign-in overlay appears over HTTPS.
  2. Click Sign In with Cognito → authenticate → redirected back with a token; your email shows in the header chip.
  3. Drag a photo in → preview → Upload Photo → success toast.
  4. Photo appears in Your Photos; click it for the lightbox.
  5. Isolation check: sign in as a second user and confirm they do not see the first user's photos.
Where to look when something fails: browser DevTools Console + Network for the failing request, and CloudWatch Logs at /aws/lambda/uploadPhoto and /aws/lambda/listPhotos.

Per-User Photo Isolation

On upload, uploadPhoto stamps each item with the owner's identity from the authorizer claims:

user_sub = event['requestContext']['authorizer']['claims']['sub']
# stored on the item as userSub (and userEmail)

listPhotos returns only items belonging to the caller, using a filtered, paginated scan:

from boto3.dynamodb.conditions import Attr

scan_kwargs = {'FilterExpression': Attr('userSub').eq(user_sub)}
# loops on LastEvaluatedKey so users with >1MB of metadata still see everything
Scaling note. A filtered Scan still reads every row before discarding non-matches — fine for a demo. For production, add a Global Secondary Index with partition key userSub and switch to table.query().

Reference: CORS & OAC Bucket Policy

CORS — apply to the PRIVATE data bucket

Required so the browser can PUT (upload) and GET (view) via presigned URLs.

[
    {
        "AllowedHeaders": ["*"],
        "AllowedMethods": ["GET", "PUT", "POST"],
        "AllowedOrigins": ["*"],
        "ExposeHeaders": ["ETag"],
        "MaxAgeSeconds": 3000
    }
]
For production, replace "AllowedOrigins": ["*"] with your CloudFront origin, e.g. "https://d1234abcd.cloudfront.net".

OAC bucket policy — apply to the PRIVATE hosting bucket

Grants only your CloudFront distribution read access. CloudFront generates this for you in Step 3 (the “Copy policy” banner); it looks like this — substitute your account ID and distribution ID:

{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Sid": "AllowCloudFrontServicePrincipalReadOnly",
            "Effect": "Allow",
            "Principal": { "Service": "cloudfront.amazonaws.com" },
            "Action": "s3:GetObject",
            "Resource": "arn:aws:s3:::aviz-photo-static-web-hosting/*",
            "Condition": {
                "StringEquals": {
                    "AWS:SourceArn": "arn:aws:cloudfront::<ACCOUNT_ID>:distribution/<DIST_ID>"
                }
            }
        }
    ]
}
No public-read policy anywhere. With CloudFront + OAC, neither bucket gets a "Principal": "*" read policy. If you copied the old static-website public policy, remove it.

Troubleshooting

SymptomLikely cause & fix
CloudFront returns AccessDenied at /No Default root object set. CloudFront → Distribution → General → Settings → set index.html.
403 from CloudFront for every fileOAC bucket policy missing/wrong, or origin points at the S3 website endpoint instead of the REST endpoint. Re-copy the policy (Step 3) and verify the origin domain ends in .s3.ap-south-1.amazonaws.com.
Old version of the site keeps loadingEdge cache. Run create-invalidation --paths "/*" after every index.html upload (Step 9).
redirect_mismatch at loginThe current page URL isn't in Cognito's callback URLs. Register both https://<dist>.cloudfront.net/ and …/index.html (Step 7d).
Distribution stuck “Deploying”Normal — initial deploy takes 5–15 min. Wait for Status = Deployed before testing.
401 Unauthorized on upload/listAuthorizer token source isn't Authorization, or the API wasn't redeployed after attaching the authorizer (Step 8).
“PHOTO_BUCKET_NAME environment variable not set”Add the env var to both Lambdas (Step 5).
CORS error on uploadData bucket missing CORS (Step 2a) and/or CORS not enabled on the API resource (Step 6c).
Broken thumbnailsPresigned URL expired (15 min) — reload. Or Lambda lacks S3 perms — check the IAM role and CloudWatch.
Upload returns 403 from S3Content-Type on the PUT doesn't match the signed type, or the presigned URL expired (5 min).
User sees others' photosOld listPhotos doing an unfiltered scan(). Deploy the version that filters by userSub.

Teardown / Cleanup

  1. CloudFront → Disable the distribution → wait until Deployed → Delete. (You can't delete an enabled distribution.)
  2. Empty both S3 buckets, then delete them.
  3. Delete the API Gateway PhotoGalleryAPI.
  4. Delete the two Lambda functions.
  5. Delete the Cognito user pool PhotoGalleryUsers (and its domain).
  6. Delete the DynamoDB table PhotoGallery.
  7. Delete the IAM role PhotoGalleryLambdaRole and the Lambda CloudWatch log groups.
aws s3 rm s3://aviz-photo-secure-data-hosting --recursive --region ap-south-1
aws s3 rm s3://aviz-photo-static-web-hosting --recursive --region ap-south-1
aws s3api delete-bucket --bucket aviz-photo-secure-data-hosting --region ap-south-1
aws s3api delete-bucket --bucket aviz-photo-static-web-hosting --region ap-south-1
aws dynamodb delete-table --table-name PhotoGallery --region ap-south-1
# CloudFront: disable in console first, then delete (or use update-distribution + delete-distribution with ETag)
Irreversible. Emptying buckets permanently destroys all uploaded photos and the website.

Final Deployment Checklist

  • DynamoDB table PhotoGallery with photoId partition key.
  • Data bucket created — public access blocked, CORS applied.
  • Hosting bucket created — public access blocked, no website hosting, no public policy.
  • CloudFront distribution created with OAC, default root object index.html, HTTP→HTTPS redirect.
  • OAC bucket policy pasted onto the hosting bucket; Status = Deployed.
  • IAM role with Lambda Basic Execution + DynamoDB + S3 access.
  • Both Lambdas deployed with PHOTO_BUCKET_NAME env var and 30s timeout.
  • REST API /photos: GET→listPhotos, POST→uploadPhoto (proxy integration); CORS enabled; deployed to prod.
  • Cognito pool + public app client + hosted UI domain.
  • Implicit grant, email+openid scopes; callback & sign-out URLs = CloudFront URL (both / and /index.html).
  • Cognito authorizer attached to GET & POST; API redeployed.
  • index.html config updated, uploaded to hosting bucket, CloudFront invalidated.
  • Test user created; full upload → view → lightbox flow works over the CloudFront URL.
  • Second user confirms they see only their own photos.
